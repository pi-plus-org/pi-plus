# Changelog

## [Unreleased]

### Fixed

- Windows without a usable shell: the built-in `bash` tool requires Git Bash (or bash on PATH) and failed on every call otherwise, inside the model loop. The `AgentSession` wrapper (`src/coding-agent/core/agent-session.ts`) now detects that case in its constructor — Windows, no user-configured `shellPath`, and `getShellConfig()` finding no bash — and excludes the `bash` tool while swapping `powershell` into its slot in the initial active toolset, so the model gets a working shell with honest PowerShell semantics. Machines with Git Bash, a user-set `shellPath`, and non-Windows platforms are untouched. Applies to both the `pipi` CLI and `pi-plus-sdk` sessions, since the SDK's `createAgentSession` resolves `AgentSession` through the same wrapper.
- Settings command hooks on Windows (`src/extensions/hooks/fire.ts`): hook commands were spawned with `bash -c` unconditionally, which throws ENOENT on Windows (swallowed, so hooks silently never fired). They now spawn via `cmd.exe` (`shell: true`, `windowsHide`) on Windows and keep `bash -c` elsewhere. Probing for bash on Windows was deliberately rejected — `System32\bash.exe` (the WSL launcher) passes a naive probe but would run hooks in the wrong environment.
- Plan mode on Windows without Git Bash (`src/extensions/plan/gate.ts`): the read-only gate blocked the `powershell` tool outright, leaving plan mode with no usable shell after the bash→powershell swap. Powershell now goes through the same two-list read-only check as bash, with PowerShell-native patterns added — read-only cmdlets/aliases (`Get-ChildItem`, `Get-Content`, `Select-String`, `gci`/`gc`/`sls`, `Resolve-Path`, `Test-Path`, …) and the POSIX aliases PowerShell shares (`ls`, `cat`, `pwd`, `sort`, `ps`) are allowed; mutating cmdlets (`Remove-Item` family, `Set-Content`, `New-Item`, `Out-File`, …), the `del`/`erase`/`rd` aliases, `Stop-Process`, and `winget`/`choco`/`scoop install` join the destructive list.

### Added

- Session recap failures surface in-session instead of on stderr (`src/extensions/recap/`): a timed-out title call (the 30s `RECAP_TIMEOUT_MS` cap, e.g. a slow provider) now shows a one-line warning in the transcript — "Session recap timed out; the session name was left unchanged." — through `ui.notify`, instead of the raw `console.error` stack trace that used to print into the TUI; other provider errors warn in the transcript too and keep their stderr log. Both are published to the new module-level `subscribeToRecapFailures` (`src/extensions/recap/events.ts`, re-exported from `pi-plus-sdk`), carrying a discriminated `RecapFailure` (`reason: "timeout" | "error"`) so embedding hosts can render their own recap status or retry; `generateRecapTitle` throws a dedicated `RecapAbortedError` to distinguish the timeout from provider errors.
- `/plan <prompt>` (plan extension `src/extensions/plan/`): any argument other than the `show` / `edit` subcommands turns plan mode on (when off) and forwards the text to the model as a user message (queued as steering while the agent is streaming), so a task can be kicked straight into the read-only planning phase from the command line.
- The plan review dialog renders the plan as markdown instead of raw text (plan extension `src/extensions/plan/component.ts`): `ExitPlanMode` presents the plan file in a scrollable rendered-markdown view with the three Claude Code choices — Approve and proceed / Stay in plan mode / Edit plan — driven by ↑↓/j/k + enter, digit keys 1-3, or esc to stay (a plain-text `ui.select` remains the fallback for RPC / headless hosts). `/plan show` reuses the same view read-only, replacing the raw `ui.notify` dump.

### Fixed

- Plan mode no longer blocks writes to the plan file itself: the plan extension's gate state moved into a module-level shared holder (`sharedPlanGateState` in `src/extensions/plan/state.ts`) that the permissions extension's "plan" permission mode keeps in sync with the mode (`syncPlanGateState` in `src/extensions/permissions/index.ts`), so both gates agree on the plan-file carve-out however plan mode is engaged. Previously the second gate ran with no plan path and rejected every `write`/`edit` to the plan file (and the model resorted to bash heredocs, which the bash allowlist also rejected); worse, plan mode engaged from the permissions side alone (Shift+Tab / `/permissions plan`) was a carve-out-less read-only mode with no plan file at all, so nothing was writable and the plan workflow tools were inert. Now permission mode "plan" always means full plan mode — the session plan file is created lazily and is the one writable path. Exiting plan mode (approval or toggle) also drops a permissions-side "plan" mode to "bypass" instead of leaving the read-only gate latched, and session replacement clears a lingering "plan" mode the same way.
- The plan-mode footer indicator renders once: the plan extension no longer sets its own `⏸ plan` status slot on top of the permissions footer's cwd-line indicator (both showed side by side while plan mode was active).

- Pinned task widget (shared core `src/extensions/tasks/`): whenever the session's task list is non-empty, a widget above the editor shows the tasks at a glance — a header with the per-status counter (`✓2 ◐1 ○3`) and one line per task (status icon, id, subject, owner, blockers; the activeForm while in progress), capped at 10 lines with an `… N more` pointer at the `/tasks` overlay — refreshed on every task mutation via a new store subscription and re-set on every `session_start` (the widget slot is cleared on session replacement). When there are no open tasks — an empty list or all completed — the widget is disposed and the slot collapses. The same counter also appears as a `tasks` entry in the footer status row. To support this, `TaskStore.forList` is now a per-process singleton per list id and the store gained `subscribe(listener)` (fired with the full post-mutation list, best-effort fan-out that never breaks the triggering operation) plus the module-level `subscribeToTasks(listId, listener)` convenience (fires immediately with the current list, then on every mutation; in-process only) for hosts that render their own task UI.
- Programmatic provider login (`src/auth/login.ts`): `loginProvider(providerId, { agentDir?, interaction?, signal?, method? })` drives pi's model-runtime login flow — the programmatic twin of the interactive `/login` — opening the provider's OAuth login page or running its API-key setup and persisting the credential to `<agentDir>/auth.json` (method defaults to oauth when the provider offers it, else api_key). `createTerminalAuthInteraction()` returns a readline-based `AuthInteraction` (numbered selects, secret prompts, device codes, auth URLs opened in the browser). Used by `pipi profile add <name> -p <provider>` (the CLI injects it into hub's `dispatchHubCommand` login hook) and re-exported from `pi-plus-sdk`.
- TUI `/login` is disabled via redirect wrappers: `src/coding-agent/modes/interactive/interactive-mode.ts` patches `InteractiveMode.prototype.handleLoginCommand` to show a status line pointing at `pipi profile add <name> -p <provider>` / `pipi profile update <name> -t <key>`, `src/coding-agent/core/slash-commands.ts` filters `login` out of `BUILTIN_SLASH_COMMANDS` so it drops from autocomplete and `/help`, and `src/coding-agent/core/auth-guidance.ts` rewrites the no-models/no-key startup guidance to the same profile-login wording (all four exports are re-implemented — the upstream formatters call `getProviderLoginHelp` in their own module scope). The entries are registered in the shared `loader/redirects.mjs` table, so the bundled `pipi` CLI, the `pi-plus-sdk` artifact, and source mode all pick them up.
- The `/init` extension (`src/extensions/init/`): the `/init` command asks the model to analyze the codebase and create `AGENTS.md` — pi's default project instructions file, already loaded into every session by upstream's context loader — at the root of the current working directory, or, when `AGENTS.md` already exists, to review it and suggest improvements instead of overwriting. A mid-session `/init` takes effect after `/reload` or in the next session. Registered by both the CLI wrapper and the SDK entry.
- Runtime settings layering for hub profiles (`src/coding-agent/core/settings-manager.ts` + `profile-settings.ts`, registered in the shared `loader/redirects.mjs` so the `pipi` CLI and the `pi-plus-sdk` both pick it up): the global settings scope reads as the agent `settings.json` deep-merged under the profile `settings.json` — nested objects merge, and the profile layer wins on conflict — so base-file edits made while a profile session runs are picked up on reload instead of only at launch. Global writes route per top-level key: the profile-scoped keys `defaultProvider`, `defaultModel`, and `defaultThinkingLevel` persist to the profile file, every other key persists to the base agent file and clears any shadow copy of it from the profile file (both layers are written under the base-then-profile lock order). The base dir resolves from the `PI_PLUS_BASE_AGENT_DIR` marker pipi records when it points `PI_CODING_AGENT_DIR` at the profile dir, and — independently of any env — whenever the agent dir is itself a hub-materialized profile dir (a direct child of `~/.pi/pi-hub/profiles`, honoring `PI_HUB_PI_DIR/PI_HUB_DIR`), so SDK hosts and manually pointed processes layer identically without inheriting pipi's environment. Any other agent dir without the marker keeps upstream single-file behavior exactly, and the project scope is untouched.
- The session recap extension (`src/extensions/recap/`, `pi-plus-session-recap`): auto-titles the session with a ≤8-word recap distilled by a one-off no-reasoning LLM call (upstream `completeSummarization`, session auth via `ctx.modelRegistry`, pattern of `src/compaction/compact.ts`), triggered when the first prompt is answered (`agent_settled` with exactly one user message on the branch) and after every compaction (`session_compact`, summarizing the new compaction summary). The title is applied with `setSessionName`, so it lands in the tab title and in the legacy resume list (which displays `name ?? firstMessage`). A persisted `pi-plus-session-recap` custom entry records each auto-set name; a name that does not match the newest marker (a manual rename, including across resume) permanently locks the session against further recaps. Runs are serialized, unpersisted sessions are skipped, and failures are logged to stderr and never surface.

### Changed

- The pi-plus sources split into three packages: this package (`@pi/plus`) is now the shared override core consumed by `@pi/plus-cli` (builds the `pi-plus` npm artifact — the `pipi` CLI) and `@pi/plus-api` (builds the `pi-plus-sdk` npm artifact). The artifact history moved to `packages/plus-cli/CHANGELOG.md`; SDK history lives in `packages/plus-api/CHANGELOG.md`. The source-mode loader and the CLI build moved to `packages/plus-cli`; the shared esbuild redirect plugin lives here at `build/redirect-plugin.mjs` and the core redirect table at `loader/redirects.mjs`.
- The extension barrel (`src/extensions/index.ts`) now exports exactly the nine non-TUI registers shared with the SDK; the CLI-only registers (`plain-tools`, `tab-title`) moved to `packages/plus-cli/src/extensions/`, and `/cd` (`src/extensions/cd/`) moved here from the CLI package so SDK hosts get the working-directory switch too.
- The direct `settings.json` readers that bypass `SettingsManager` gained the base agent layer, so hub-profile runs see general keys that the materializer no longer bakes into the profile copy: the command-hooks loader (`src/extensions/hooks/loader.ts`) merges hooks from `~/.pi`, the base agent settings, the agent dir, and the project settings files, and the memory settings reader (`src/extensions/memory/settings.ts`) resolves `memory` with precedence project > agent dir > base agent dir > `~/.pi`.
- The layer stack those readers duplicate is now shared in `src/coding-agent/core/settings-layers.ts`: `getSettingsLayerPaths` (the four files in increasing precedence), `readLayeredSetting` (first-wins value read with a per-feature validator — used by the memory settings reader and the `/vim` flag in `packages/plus-cli`), and `writeLayeredSetting` (persists a general key to the base agent settings under a hub profile — or the agent dir otherwise — preserving other keys and dropping stale profile shadows). The hooks loader keeps its own additive merge but walks `getSettingsLayerPaths`.
- Context-guard token-usage detection (`src/extensions/context-guard/`) now refreshes after every thinking block, tool execution, and response instead of only at turn boundaries: a new `message_end` handler on all message roles estimates the projection plus the just-finished message, so the `PI_MAX_ACTIVE_MESSAGES` force trigger calls `ctx.compact()` mid-run (a run-scoped flag, reset on `agent_start`/`agent_settled`, keeps the rest of the batch and the interrupted run's `turn_end` from re-firing) and an over-threshold message marks the turn for pruning even if the `turn_end` estimate later dips below the threshold. Prune `context_edit` drafts can still only be emitted from boundary events, so `turn_end` keeps applying them against the complete projection; its message-count check is skipped when the per-message trigger already fired.

### Fixed

- Session recap (`src/extensions/recap/generate.ts`): a `length` stop (the title call hit its 128-token output cap, e.g. a provider that reasons by default or a model that rambles) no longer fails the whole recap. The strict upstream `getSummarizationFailure` check — right for compaction checkpoints, where a truncated summary must never persist — is replaced with recap-specific handling that salvages the partial output through `sanitizeRecapTitle` (first line, word-boundary-truncated), throwing only when no usable title survives; provider errors and aborts remain fatal.
- Command hooks fire with the session's working directory instead of the process cwd (`src/extensions/hooks/`): the register extension passes `ctx.cwd` in the `fireUserHooks` fields for `PermissionRequest`, `PreToolUse`, and `Stop`, and `fireUserHooks` uses it (falling back to `process.cwd()`) for the payload's `cwd`, the working directory hook children spawn in, and the settings lookup. Previously SDK hosts whose process cwd is not the session's — e.g. the desktop app, whose main process runs with cwd `/` — sent `"cwd":"/"` in every payload, spawned hooks in `/`, and never matched project-level `.pi/settings.json` hooks.

### Removed

- The plan review "Edit plan" choice (plan extension `src/extensions/plan/`): the canonical `PLAN_REVIEW_CHOICES` / `PlanReviewDialogChoice` no longer include `edit` — `ExitPlanMode` review presents Approve & auto-accept edits / Approve & bypass permissions / Stay in plan mode (digits re-keyed to 1-3), and the review-time editor flow was dropped from `resolveReviewPick` and the tool result. Host dialogs that still return `"edit"` are treated as stay; manual plan editing remains available via `/plan edit`.
